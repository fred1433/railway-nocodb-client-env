Limits and decisions

  1. Private tunnel rather than a public Railway domain: a second public path would go around Access.
  2. Access in front of NocoDB Community leaves a second login: a token that passes Access still gets HTTP 401 from NocoDB.
  3. Access was tested with service tokens. Human sign-in was not tested.
  4. Since 9 January 2026 the NocoDB license reads: “Internal self-hosting does not require a commercial license”, while a commercial license is needed to “Offer NocoDB as a hosted or managed service” or to “Provide direct NocoDB access to external customers”. The question is who uses NocoDB, and who owns the instances.
  5. QuickBooks webhooks need a non-interactive endpoint with signature validation. The OAuth callback route must be tested separately.
  6. Read-only NocoDB is a choice for this example, not a rule of the setup. Edits would need a role with write grants.
  7. On NocoDB 2026.10.1, NC_INVITE_ONLY_SIGNUP=true left sign-up open on the first run: HTTP 200 and users 1 to 2 (first-run checks, commit 02f76ee). The bootstrap now sets the admin setting and checks it before the tunnel starts.
  8. NocoDB 2026.10.1 reached 0.99 GB in these two environments and rested near 0.72 GB. In a feasibility test under a 512 MB service limit it did not start in the settings tried (record).
  9. Railway cron schedules are in UTC, so the local time of a backup moves with daylight saving.
  10. Outside this example: real QuickBooks; GitHub repositories, teams and access per client; n8n.
